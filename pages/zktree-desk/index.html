The tree that remembers every transfer

Quantus keeps a 4-ary Poseidon Merkle tree over every transfer on the chain — one leaf per transfer, folded once per block, its root published in the block header. It is the backbone of the wormhole privacy exits: your ZK proof of "I was paid" is a Merkle path in this tree. This desk watches it live, recomputes its hashes exactly, and lets you prove things against it.

How leaves get in

  • Every block the mining-rewards pallet records the block reward — that is the ≥ 1 leaf/block floor (pallets/mining-rewards/src/lib.rs).
  • SafeSend reversible transfers and vesting payouts each record a leaf per transfer (pallets/reversible-transfers, pallets/vesting).
  • Leaves are appended during the block (UnprocessedLeaves counts them) and folded into the tree once per block in on_finalize — the root you read mid-block covers the previous block's leaves.
  • Only leaves already folded are provable: get_merkle_proof returns LeafNotYetSettled for this block's fresh leaves.

Hash a leaf to see its 8-felt preimage.
Why is from not in the leaf? Uniqueness comes from (to, transfer_count) — each recipient's counter only moves forward, so every transfer to them gets a unique index. The sender is irrelevant to proving "I received funds once".
The lossy-encoding invariant. Each 8-byte limb is reduced mod the Goldilocks prime, so a recipient and its non-canonical byte-alias hash identically. The wormhole keys transfer counts on the canonical form so two deposits can never commit to the same leaf (and the same nullifier). This desk canonicalizes before hashing and tells you when it had to.
Two decimals of privacy. Amounts are quantized to amount / 1010 (2 QTC decimals) and committed as a u32 — oversized values saturate at u32::MAX rather than wrapping, so a huge transfer can never alias a small one in the tree.

Batched folding. The runtime does not rehash the path on every insert — inserts only append, and on_finalize folds the whole block's range in one bottom-up pass (~n/3 node hashes instead of n · depth). Pressing "Finalize block" runs that same fold here.
Sorted children. Proofs need no path indices because every node sorts its 4 children before hashing — the verifier just sorts and hashes. Try it: the simulator hashes children in shuffled order and still lands on the same node.

🌀 Wormhole & circuits — what the tree is for

    

      
The tree is the commitment layer for private exits. When a transfer is recorded, its leaf
      commits to (recipient, per-recipient count, asset, quantized amount) — no sender, no secrets. Later,
      the recipient proves in zero knowledge: "some leaf in this tree paid me, and I know the secret that lets
      me spend it". The wormhole pallet checks that proof with verify_private_batch /
      verify_public_batch (pallet 20) and enforces one-spend-per-leaf with nullifiers.

      

        
1Recordtransfer → record_transfer → leaf appended

        
2Foldon_finalize folds the block's leaves; root → block header

        
3Proverecipient fetches ZkTreeApi_get_merkle_proof, builds a ZK proof off-chain

        
4Exitwormhole verifies the batch proof; nullifier blocks replays

      

      
The depth-16 circuit ceiling

      
The chain lets the tree grow to depth 32, but the deployed ZK circuits only accept proofs up
      to depth 16 — every leaf proof pays a full 16-level path, so the cap keeps proving fast.
      416 ≈ 4.29 billion leaves. If the tree ever outgrows it, proof generation halts until
      a circuit update + runtime upgrade raises the ceiling — a deliberate "fix it when we get close" trade-off,
      documented in pallets/zk-tree/src/lib.rs. LeafCount is public storage, so exhaustion
      is visible years in advance.

Honest limits

    
    
      
  • This desk recomputes hashes and verifies proofs — it does not generate ZK proofs or perform wormhole exits; proving needs the off-chain circuit crates.
    • 
      
  • Leaf contents (recipient, amount) are public on-chain data — the tree commits to transfers, it does not hide them. Privacy comes from the ZK proof layer on top.
    • 
      
  • Amounts in leaves have only 2 decimals of precision; dust below 1010 plancks quantizes to zero in the commitment.
    • 
      
  • The "live" views need a reachable node; this page never fabricates chain state when the node is down.
